## Схема иерархии

Иерархия имеет три уровня:

```text
BR — Brazil
└── ST:<state> — штат
    └── CT:<state>:<city> — город
```

Для каждого штата в дерево включается не более 20 городов с максимальным числом клиентов.

Пример для варианта 3:

```text
BR
└── ST:MG
    ├── CT:MG:<город 1>
    ├── CT:MG:<город 2>
    └── ...
```

Конкретные города выбираются из реальных значений `olist.customers`.

## Пример path

Для прямого обхода от MG путь формируется так:

```text
MG > Belo Horizonte
```

Название конкретного города зависит от данных Olist.

Для обратной рекурсии путь строится от выбранного города к родителю:

```text
<город> < MG < Brazil
```

## Как работает рекурсивный CTE

`WITH RECURSIVE` состоит из двух частей.

**Базовая часть** создаёт начальный набор строк. В прямой рекурсии это узел `ST:MG`.

**Рекурсивная часть** соединяет уже найденные узлы с `lab.geo_tree` по условию:

```sql
child.parent_id = parent.node_id
```

На каждой итерации добавляется следующий уровень дерева. Выполнение заканчивается, когда рекурсивная часть больше не находит новых строк.

В обратном запросе логика меняется: начиная с города, запрос на каждом шаге ищет строку, у которой `node_id` совпадает с `parent_id` текущего узла, пока не дойдёт до `BR`.

## VIEW и MATERIALIZED VIEW

`VIEW` хранит только определение запроса. При обращении к нему PostgreSQL получает актуальные данные из исходных таблиц.

`MATERIALIZED VIEW` физически хранит результат запроса. Поэтому чтение может быть быстрее, но после изменения исходных данных результат нужно обновить командой:

```sql
REFRESH MATERIALIZED VIEW lab.mv_monthly_state_sales;
```

## Защита от циклов

Если в иерархии случайно появится цикл, обычный рекурсивный запрос может повторно обходить уже посещённые узлы. В дополнительном задании используется массив `path_ids`. Перед добавлением следующего узла проверяется:

```sql
WHERE NOT (g.node_id = ANY(s.path_ids))
```

То есть узел не добавляется, если он уже присутствует в текущем пути.
